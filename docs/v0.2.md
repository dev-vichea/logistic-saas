# Mekong v0.2 — Customer & Business Partner Management

## Delivered changes

v0.2 adds a private external business directory to the existing v0.1 modular monolith. It preserves the workspace design, session authentication, organization switching, existing role rules, team/department management and audit APIs. No operational shipment, dispatch, quoting, booking or finance workflows are implemented.

- Partner company profiles support customer, shipper, consignee, supplier, carrier, freight forwarder, broker and warehouse operator roles; one company may have several roles.
- Profiles store legal and display names, optional tenant-unique reference code, global HQ country, registration/tax identifiers, email/phone/website and operational notes.
- Contacts and locations have independent CRUD endpoints and paginated profile sections. Primary reassignment is atomic and backed by partial unique indexes.
- Reusable locations keep their own address, country, type and optional coordinate pair. Stable IDs and tenant-qualified keys prepare future workflow references without building those workflows now.
- Archive/restore retains child data and provides a reversible, audited lifecycle. Archived partners are read-only and excluded from the default list.
- List search, role/country/status filters, sorting and pagination run in Laravel/PostgreSQL. Frontend query controls persist in the URL.

## Upgrade

Back up the database and review the additive `create_partner_directory_tables` migration. Run `php artisan migrate --force`, reload the application processes, and restart queue workers as usual. The migration creates three new tables plus indexes/constraints; it does not rewrite v0.1 data. No directory data is automatically seeded, imported, linked to another Mekong organization or shared. There are no new environment variables or package dependencies.

The existing `/api/v1` prefix and first-party cookie contract remain unchanged. The OpenAPI document is now release 0.2.0 and contains 17 additional operations. Partner-specific catalogs use `/organizations/{organization}/partners/catalog`; the existing regional organization catalog is preserved.

## Permissions

| Capability | Owner | Admin | Manager | Member | Viewer |
|---|---|---|---|---|---|
| View directory and child records | Yes | Yes | Yes | Yes | Yes |
| Create/edit partners, contacts and locations | Yes | Yes | Yes | Yes | No |
| Delete contacts and locations from active partners | Yes | Yes | Yes | Yes | No |
| Archive/restore partners | Yes | Yes | Yes | No | No |

All writes reuse the v0.1 organization lock and re-read membership permissions. Every child route resolves the parent through the authenticated organization. The database rejects foreign-tenant parent assignments, and API payloads cannot reparent records or set archival timestamps directly. Audit events commit with each successful mutation and exclude private company/contact/location values.

## Validation and practical limits

Run `make test` and `MAILPIT_URL=http://localhost:8025 npm run test:e2e` from `frontend` for the complete regression checks. See `testing.md` for dedicated database requirements. Production build/browser checks should use `next start`, as in CI.

Partner names are not unique; optional reference codes are unique per tenant even after archival. There is no automated duplicate-company merge, account invitation, geocoding, external synchronization, import/export or cross-company sharing in this release. Leading-wildcard substring search is bounded by organization and capped pagination; add measured search-index improvements when real directory size requires them. Future shipment references must preserve tenant ownership and restrict deletion of used locations; snapshot address data for historical records when needed.
